# HomeFleet v0.5.5 — model status that catches up

**A model server started after the daemon now shows up as `ok` within a minute.** The daemon used to probe its model catalog only at startup, so a llama-server started later (it doesn't come back on its own after a reboot) stayed `unreachable` in `homefleet nodes`, `homefleet status` and the dashboard until the daemon restarted. The probe now repeats every 60 s.

Real-hardware status: v0.5.5 is pushed to the rig with `homefleet fleet upgrade` from a laptop that already runs v0.5.4. That run is also the first hardware check of v0.5.4's saved rollout status: the CLI should report the tower correctly after the laptop's own restart. It follows publishing; see the devlog.

## What's new
- **Model catalog re-probe every 60 s.** The same check as at startup: one `GET /models` per model server, at most one probe in flight, stopped with the daemon. Status stays advisory; nothing gates on it.
- **Two flaky tests are fixed.**
  - The oversized-body 413 test in `mcp/http-transport.test.ts` raced the server's close on Windows CI. It now sends only the request headers, so the assertion stays strict (exactly 413) without the race.
  - The concurrent-push test in `upgrade/coordinator.test.ts` assumed the first of two simultaneous pushes always wins. Either may win, and the coordinator always accepted exactly one and refused the other; the test now checks exactly that. No behavior change.

## Known limitations
- **No on-demand re-probe.** A just-started model server can take up to 60 s to show as `ok`.
- Everything listed for [v0.5.4](v0.5.4.md) and earlier still applies.

## Install
On a v0.5.2+ fleet, from one node:
```bash
homefleet fleet upgrade
```
On a single v0.5.0+ node:
```bash
homefleet upgrade
```
Fresh install, or from v0.4.0 or older:
```bash
npm i -g https://github.com/Hugodzl/HomeFleet/releases/download/v0.5.5/homefleet-0.5.5.tgz
```
See the [README](https://github.com/Hugodzl/HomeFleet/blob/v0.5.5/README.md#install).
