# HomeFleet v0.5.4 — a sturdier fleet rollout

**Hardening for `homefleet fleet upgrade`.** The follow-ups from the Phase 3 final review, plus the one real bug the first fleet push on the rig turned up: when the requesting node restarts to upgrade itself, the rollout's outcome now survives, so the CLI no longer reports a peer's stale state.

Real-hardware status: v0.5.3 was pushed laptop → tower with `homefleet fleet upgrade` in 14 s (devlog 023). v0.5.4's rig run, a fleet push in which the laptop also upgrades itself last, follows publishing. The changes below are covered by unit tests and the daemon integration tests (1181 passing).

## What's new
- **The rollout outcome survives the requester's own restart.** The final rollout status is written to `<data dir>/upgrades/rollout-status.json` at every final step and at the self hand-off. After the restart, `GET /control/upgrades` serves it back, with this node's own result settled from its fresh `lastUpgrade`, and `homefleet fleet upgrade` re-reads it instead of summarizing its last poll. A peer that refused between two polls is now reported as `refused`, not as `pushing`.
- **Stopping the daemon stops a rollout.** A rollout still waiting on a peer ends at its next step, is marked `stopped` ("the daemon stopped during the rollout"), and never upgrades this node.
- **No false stop from a stale record.** A peer named with `--nodes` that wasn't reachable at selection gets a `hello` just before the push, so an old failure record for the same version can't be mistaken for this rollout's.
- **Endpoints are re-resolved on every poll**, so a peer that comes back on a new address after its restart is still seen.
- **Peer-facing refusal wording.** A pushed node no longer sends its local install path ("not installed") or CLI advice ("pass --force") to the requesting node.
- **Both download failures are reported.** When the download fails from the requester and then from GitHub too, the recorded reason names both sources.
- **More route tests:** `UPGRADE_BUSY` 409, an unpaired client gets 401 on both upgrade routes, and percent-encoded traversal on the tarball route returns 404.

## Known limitations
- Everything listed for [v0.5.2](v0.5.2.md) and [v0.5.3](v0.5.3.md) still applies: peers need `"upgrade": { "allowRemote": true }`, only v0.5.2+ peers accept a push, on Windows `homefleetd` must run outside packaged apps, the dashboard trigger and per-boot control token are Phase 4, Windows-first, not on the npm registry.
- **One requester at a time.** Two nodes running rollouts that target each other aren't coordinated.

## Install
On a v0.5.2+ fleet, from one node:
```bash
homefleet fleet upgrade
```
On a single v0.5.0+ node:
```bash
homefleet upgrade
```
Fresh install, or from v0.4.0 or older:
```bash
npm i -g https://github.com/Hugodzl/HomeFleet/releases/download/v0.5.4/homefleet-0.5.4.tgz
```
See the [README](https://github.com/Hugodzl/HomeFleet/blob/v0.5.4/README.md#install).
