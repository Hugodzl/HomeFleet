# HomeFleet v0.5.0 — signed releases and self-upgrade

**This is the last release you install by hand.** Every release now ships a manifest signed with HomeFleet's release key, and `homefleet upgrade` uses it to move a node to a newer release: it downloads the release, checks the signature against a key pinned in the code, installs it, restarts the daemon in the background and rolls back to the previous version if the new one doesn't come up. v0.5.0 also adds `homefleet unpair`.

Real-hardware status: `homefleet unpair` was checked on the laptop on 2026-09-25 against two throwaway daemons (preview without `--yes`, unpair by an 8-character ID prefix, trust and known-nodes emptied, the peer left one-sided as designed — devlog 020). `homefleet upgrade` is covered by tests that drive the real updater script with a fake `npm` and a fake daemon (success, rollback after a failed health check, rollback after a failed install, no rollback copy), but it **can't be proven on hardware until there is a release to upgrade to**: the first real run is 0.5.0 → 0.5.1, along with a forced-rollback test on the tower.

## What's new
- **Signed release manifests.** Each release carries `homefleet-X.Y.Z.manifest.json` (version, sha256, size, HFP version) and `homefleet-X.Y.Z.manifest.sig` (a detached Ed25519 signature). The release workflow signs, then verifies against the pinned public key, before anything is published. The signing key lives on an approval-gated GitHub environment that only `main` and `v*` tags can reach.
- **`homefleet upgrade [--to <version>] [--check] [--force]`.** The running daemon does the work: it resolves the target, downloads and verifies it, runs its pre-flight checks and caches a rollback copy, all before anything stops. Then a small detached updater replaces the install, relaunches the daemon and checks that it answers on the new version. The CLI waits up to 3 minutes and reports `succeeded`, `rolled-back` or `failed` with the reason; `GET /control/status` keeps the last outcome as `lastUpgrade`.
- **Pre-flight refusals leave the node untouched:** a target that isn't newer (no downgrades), a protocol major-version change, running jobs (unless `--force`), and a daemon run from a git checkout rather than an `npm i -g` install.
- **`homefleet unpair <name|deviceId> [--yes]`.** Revokes trust in a paired peer on the running daemon: its requests are refused from then on, its jobs on this node are canceled, and agents can no longer follow up on jobs sent to it. One-sided by design: run it on the peer too.
- **Control API:** `GET /control/upgrade/check`, `POST /control/upgrade` and `POST /control/unpair`, behind the same loopback, Host-header and `x-homefleet-control` defenses as every other control route.

## Known limitations
- **Upgrading to v0.5.0 is manual** (`npm i -g` the tarball below). Releases up to v0.4.0 have no signature, so they can never be upgrade targets or rollback copies.
- **Self-upgrade is unproven on hardware** until v0.5.1 (see above).
- **Local only:** `homefleet upgrade` upgrades the node you run it on. Pushing an upgrade across the fleet over HFP, and triggering it from the dashboard, are the next phases.
- **Checkout-run daemons are refused** (`not-installed`); update those with git + `pnpm build`.
- **Same-user loopback boundary, no per-boot token yet:** the upgrade route can only install a release that verifies under the pinned key, never caller-supplied bytes. The dashboard gets no upgrade button until the per-boot token lands.
- **Not on the npm registry yet** — install from the Release asset URL.
- **Pre-alpha, Windows-first.** Linux runs in CI; macOS is untested.

## Install
```bash
npm i -g https://github.com/Hugodzl/HomeFleet/releases/download/v0.5.0/homefleet-0.5.0.tgz
homefleet upgrade --check
```
