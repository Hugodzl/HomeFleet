# HomeFleet v0.3.0 — packaged install + per-node model catalog

**HomeFleet now installs with one command.** v0.3 is the first packaged release: every `v*` tag builds `homefleet-<version>.tgz`, installs that exact file on fresh Ubuntu and Windows machines, runs the installed daemon, and only then attaches it here. With Node ≥ 20, `npm i -g <tarball URL>` puts `homefleetd`, `homefleet` and `homefleet-mcp-stdio` on your PATH — no clone, no pnpm, no build. It also makes each node's model set an explicit, enforced catalog instead of whatever its model server happened to serve.

Proven on real hardware (2026-09-24): both rig machines installed this release from its public URL, kept their existing identities and pairings, and passed command delegation in both directions plus a write job in which the tower's local Qwen3.6-35B-A3B wrote a test that landed on the laptop and passed.

## What's new
- **Packaged install (S1).** A GitHub Releases tarball whose manifest is generated from `@homefleet/daemon`: first-party code is bundled into the bins, third-party deps resolve from the registry at install time. The release workflow gates on lint/typecheck/tests, refuses a tag that doesn't match the package version, and smoke-tests the *installed* product (daemon start, `status`/`nodes`/`setup`, an MCP handshake through the stdio shim) on both OSes before publishing.
- **Per-node model catalog (A2).** `catalog.models` is the single source of model truth on a node: each model is validated against its server (`status: ok | unreachable | …`) and advertised in capabilities. A job asking for a model the target doesn't offer is refused with `MODEL_NOT_OFFERED` — on the worker, and now also on the delegator *before* the workspace sync, so a bad model id no longer ships a whole bundle first. Pre-catalog configs auto-migrate. Protocol → **HFP 0.3.0**.
- **Model targeting for write jobs** through the MCP `delegate_task` tool, with catalog status passed through in `list_nodes`.

## The theme: test what the user runs
The packaging bug worth knowing about was invisible from a checkout: under a Linux global install every bin is a symlink, and the old entry guard compared `import.meta.url` (real path) with `argv[1]` (link path) — so every command would have exited 0 having done nothing, and a smoke test that only checked the exit code would have passed it. The guard now compares real paths, and the release smoke asserts real output from the installed daemon rather than an exit code. Full write-up in devlog 017.

## Also this cycle
- `scripts/pack-release.ts` (`pnpm pack:release`) builds the tarball locally; its integration test asserts the tarball's exact file list, so a stray file fails CI instead of shipping.
- A v0.1 debt-list audit: two items were long since fixed; the mDNS probe race is genuinely open and needs an upstream fix or a patch (devlog 016).

## Known limitations
- **Not on the npm registry yet** — install from the Release asset URL. The artifact is already publish-shaped for when that changes.
- `homefleet setup` still prints a stale "run `pnpm build` first" hint, and redirected daemon logs show `—`/`…` garbled in Windows PowerShell 5.1 — both fixed in 0.3.1.
- **Pre-alpha, Windows-first.** Linux runs in CI; macOS is untested.

## Install
```bash
npm i -g https://github.com/Hugodzl/HomeFleet/releases/download/v0.3.0/homefleet-0.3.0.tgz
homefleet setup
```
