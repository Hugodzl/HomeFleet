# HomeFleet v0.6.0 — upgrade from the dashboard

**The dashboard can now push an upgrade.** Open `homefleet dashboard`, and when a newer release exists the nodes that can take it carry an "available" badge. **Upgrade all**, a button on each peer and a button for this node start the same signed, sequential rollout as `homefleet fleet upgrade`, without a terminal. No protocol change: this is the loopback control API and the page only (HFP stays 0.4.0).

Real-hardware status: not yet proven. The rig run (a v0.6.1 pushed from the dashboard, including this node's own restart and the page reload) happens after publishing; see the devlog.

## What's new
- **Upgrade buttons.** Upgrade all (`targets: "fleet"`), a button per peer (that peer only; this node is not included), and one for this node. Peers go first and this node last, as with the CLI, and the rollout stops at the first failure.
- **Verify, then confirm.** Each button first calls the new `POST /control/upgrade/prepare`, which downloads the release and checks its signature, hash and size without starting anything. The confirm dialog opens on a verified release (or shows the error). It lists what will happen: a busy peer is shown as refused, because remote pushes never force. Only this node can be forced, with an explicit checkbox.
- **Live progress and automatic reload.** The page shows each node's step from the rollout status. This node's restart replaces the daemon, its assets and its token, so the page reloads once afterwards (at most once per 10 s) instead of going stale.
- **A per-boot control token.** The daemon makes a new 64-character hex token at every start, writes it to `<dataDir>/control-token` (mode 0600), embeds it in the dashboard page, and requires it in the `x-homefleet-control-token` header on `POST /control/upgrade` and `POST /control/upgrade/prepare` only. A missing or wrong token gets a 403 `bad-token` before the body is read. Every other route is unchanged. The CLI reads the token from the file.
- **`includeSelf`.** `POST /control/upgrade` accepts `includeSelf: false` to push to the chosen peers only. The default is `true`, so the CLI's `--nodes` behavior is unchanged.
- **`availableUpgrade` badge.** `GET /control/status?dashboard=1` adds the latest release when it is newer than this daemon. The lookup is cached for 6 hours (15 minutes after a failed one, with no field); a plain status call never touches the network. A peer gets a badge only if it is reachable, new enough for remote upgrade, has `allowRemote` on, and is behind.

## Compatibility and upgrading
- **The CLI and the daemon must both be v0.6.0 or later for upgrade commands.** An older CLI does not send the token, and a v0.6.0 daemon answers `Refused: the daemon's control token didn't match`. Upgrade the CLI and the daemon together (`npm i -g` installs both).
- **Peers on older versions can still be upgraded.** The token is local to each daemon's control port; it is not part of HFP. A v0.5.2+ peer with `upgrade.allowRemote` takes the push as before; older nodes still need a local `homefleet upgrade`.
- The token changes at every restart, so an open dashboard tab from before a restart reloads itself on its next request.

## Known limitations
- **Not proven on hardware yet.** See above.
- The dashboard still cannot rename, edit config, pair or cancel; upgrade is the only write.
- The token protects against a web page and other origins, not against another process running as the same OS user, which could read the file. The trust boundary is unchanged.
- Everything listed for [v0.5.5](v0.5.5.md) and earlier still applies.

## Install
On a v0.5.2+ fleet, from one node:
```bash
homefleet fleet upgrade
```
On a single v0.5.0+ node:
```bash
homefleet upgrade
```
Fresh install, or from v0.4.0 or older:
```bash
npm i -g https://github.com/Hugodzl/HomeFleet/releases/download/v0.6.0/homefleet-0.6.0.tgz
```
See the [README](https://github.com/Hugodzl/HomeFleet/blob/v0.6.0/README.md#install).
